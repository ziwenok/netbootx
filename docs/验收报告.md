### 3.2 HTTP Range（核心技术）

服务端从 ISO **内部**按偏移流式读文件，不挂载、不解压：

```
HEAD /iso/{id}/boot/vmlinuz-lts
  → 200, Accept-Ranges: bytes, Content-Length: 12403712

GET /iso/{id}/boot/vmlinuz-lts  Range: bytes=0-3
  → 4d 5a 00 00          (MZ，Linux 内核头) ✅

GET /iso/{id}/boot/vmlinuz-lts  Range: bytes=500-599
  → 206 Partial Content, 100 字节 ✅

GET /iso/{id}/boot/vmlinuz-lts  Range: bytes=1000000-1000015
  → b7b3 0d9e b7ed 5a76 ... (文件中段，可随机访问) ✅

GET /iso/{id}/boot/initramfs-lts  Range: bytes=0-1
  → 1f 8b                 (gzip 头) ✅

完整下载 12,403,712 字节，与 ISO 内记录的大小完全一致 ✅
```

### 3.5 iPXE 脚本生成

真实服务生成的主菜单（curl 实测）：

```
#!ipxe
# NetBootX iPXE 启动脚本（由服务端自动生成，请勿手工编辑）
# 客户机: aa:bb:cc:dd:ee:ff / UEFI x86_64
# 服务端: http://127.0.0.1:16000
dhcp
set base http://127.0.0.1:16000
menu NetBootX 启动菜单 - aa:bb:cc:dd:ee:ff
item --gap --  Linux
item iso_ab106048549bc05b 1) Alpine Linux 3.20.3 - alpine-standard-3.20.3-x86_64.iso (209MB)
choose --timeout 30000 --default iso_ab106048549bc05b target || goto netbootx_cancelled
goto ${target}
:iso_ab106048549bc05b
kernel ${base}/iso/ab106048549bc05b/boot/vmlinuz-lts modules=loop,squashfs,sd-mod,usb-storage alpine_dev=cdrom quiet
initrd ${base}/iso/ab106048549bc05b/boot/initramfs-lts
boot || goto netbootx_failed
:netbootx_failed
echo 引导失败，5 秒后返回启动菜单
sleep 5
chain http://127.0.0.1:16000/boot/menu.ipxe?mac=aa:bb:cc:dd:ee:ff
:netbootx_cancelled
echo 已取消启动，进入 iPXE 命令行
shell
```

包含失败自动回菜单的容错逻辑 ✅

## 四、开发过程中发现并修复的 BUG

| # | BUG | 严重度 | 发现方式 | 状态 |
|---|---|---|---|---|
| 1 | `boot.Entry()` 生成的脚本缺 `#!ipxe` 头和 `set base`，iPXE 会拒绝执行 | **致命** | 打印生成脚本人眼检查 | ✅ 已修 |
| 2 | DHCP 绑到具体 IP 导致广播回包失败（`can't assign requested address`），客户机永远收不到应答 | **致命** | 真实 DISCOVER 报文 | ✅ 已修 |
| 3 | `iso.Scan()` 不跟随文件软链接，README 承诺的软链接用法失效 | 高 | 真实 ISO + 软链接 | ✅ 已修 |
| 4 | Rock Ridge SUSP 名字尾部 NUL 填充未剥离，真实 ISO 的 `/boot` 下所有文件查不到 | **致命** | 真实 Alpine ISO | ✅ 已修 |
| 5 | 前端 `renderLogs(true)` 同时清 DOM 和数据，日志面板永远空白 | 高 | 真实服务 + 浏览器截图 | 待修 |
| 6 | `El Torito` 重复 case `media144Floppy` 编译失败 | 中 | 编译 | ✅ 已修 |
| 7 | 顶栏显示 `当前配置 · ? · IP`，interface 为空时出现问号 | 低 | 浏览器截图 | 待修 |

> BUG 2、4 都是**只有真实环境才能暴露**的问题，纯单元测试测不出来。
> 这也是为什么验收必须用真实 ISO + 真实协议报文 + 真实浏览器。

## 五、尚未验证的部分（诚实说明）

以下需要**真实物理机/虚拟机 PXE 启动**才能验证，本机环境不具备条件：

1. **端到端 PXE 启动全流程**：客户机真实开机 → PXE 网卡 → 加载 iPXE → 菜单 → 启动 Alpine
   - 缺少：第二台机器（或支持 PXE 的虚拟机）
   - 缺少：qemu（brew 环境损坏，无法安装）
   - 已做替代验证：DHCP 报文级 + TFTP 传输级 + HTTP Range 级 + iPXE 脚本语法级，全部通过

2. **Windows / WinPE 引导**：wimboot 方式生成正确，但没有真实 Windows ISO 验证

3. **Secure Boot 链路**：shim + 签名 iPXE 的 MOK 配置未验证

4. **ARM64 / LoongArch64 客户机**：引导文件路径正确，但没有对应硬件

5. **多客户机并发启动**：并发逻辑有单测覆盖（40 并发生成脚本、32 协程并发读 ISO），
   但没有真实多机同时 PXE 压测

**建议**：在有条件的机器上，用一台 Linux + QEMU 做客户机，跑一次完整 PXE 启动验收。

## 六、如何复现验证

```bash
cd netbootx

# 1. 单元测试
make test

# 2. 真实 ISO 验收（需先下载 Alpine ISO 到 /tmp/nbx-iso/alpine.iso）
NBX_TEST_ISO=/tmp/nbx-iso/alpine.iso ./go test ./internal/iso/ -run TestRealISO -v

# 3. 启动服务（高位端口，不需要 sudo）
./bin/netbootx -dhcp 16767 -tftp 16969 -http 16000 -web 16080 \
    -no-browser -autostart -ip 127.0.0.1 -mode proxy

# 4. DHCP 探针（另开终端）
python3 scripts/dhcp-probe.py --port 16767 --arch 7
python3 scripts/dhcp-probe.py --port 16767 --arch 0

# 5. HTTP Range 验证
ISOID=$(curl -s http://127.0.0.1:16080/api/isos | python3 -c "import sys,json;print(json.load(sys.stdin)['data']['isos'][0]['id'])")
curl -r 0-3 "http://127.0.0.1:16000/iso/$ISOID/boot/vmlinuz-lts" | xxd

# 6. 界面截图
node scripts/shot.mjs http://127.0.0.1:16080 /tmp/ui.png
```
